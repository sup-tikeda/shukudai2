# バイクショップ店舗管理

TanStack Start + Vite / ark-ui / Tailwind CSS + Tailwind Variants / zod / better-auth / drizzle-orm /
PostgreSQL / Vitest 構成の、バイクショップ（二輪整備・販売店）向け受付管理アプリです。
FileMaker製の同名アプリ（`バイクショップ店舗管理.fmp12`）のDDR（設計情報）解析結果をもとに、
テーブル構成・画面構成を移植しています。ログイン・認証の仕組みは以前の練習課題
（社内備品貸出管理）からそのまま引き継いでいます。

**現在の構成**：アプリは **Cloudflare Workers**、DBは **Neon（PostgreSQL）** で動いており、
接続は **Hyperdrive** を経由します（PCの電源に関係なく常時稼働）。

| --- | --- |
| 公開URL | https://shukudai2.t-ikeda-09f.workers.dev |
| リポジトリ | https://github.com/sup-tikeda/shukudai2 |

一番簡単な鍵のかけ方）をかけています。IDとパスワードはこのREADMEには書かず、別途お伝えします。

## 機能

- ログイン（アカウント名／パスワード。自己登録は不可で、初期アカウントはCLIで発行）
- ログイン後のダッシュボード（`/`）から各画面へ遷移
- 顧客管理（`/customers`、`/customers/$id`）：顧客の登録・編集・削除、保有車両の一覧
- 車両管理（`/vehicles`、`/vehicles/$id`）：車両（バイク）の登録・編集・削除、関連する案件の一覧
- 案件管理（`/cases`、`/cases/$id`）：整備・修理などの作業案件の登録・編集・削除、関連する見積・請求の一覧
- 見積・請求管理（`/quotes`、`/quotes/$id`）：見積書・請求書の作成、明細項目の追加・編集・削除と自動集計
  （数量・税抜合計・消費税額・税込合計はすべて明細から都度計算し、保存はしない）
  - 明細項目ごとに消費税率を持てる（軽減税率・非課税品目が混在しても正しく計算される）
  - 見積書から請求書へのワンクリック変換（元の見積書は証跡として残す）
  - 発行日（作成日）を後から編集可能。社内メモ（帳票に印字されない）を通信欄とは別に持てる
- 見積書・請求書のPDF出力（`/quotes/$id/print`）：会社設定を差し込んだ帳票を表示し、
  ブラウザの印刷機能でPDFとして保存（「[見積書・請求書のPDF出力](#見積書請求書のpdf出力)」参照）
- 社内チャット（`/chat`）：登録した社内規定について質問できる（Gemini APIを使用）
- 設定（`/master`。ナビ右側に表示。admin権限のみ）
  - 会社設定：見積・請求書に印字する自社情報と既定の消費税率（全体で1レコードのみ）
  - 社員マスタ：ログインアカウント（名前・アカウント名・権限・パスワード）に加え、
    ふりがな・生年月日（年齢は自動計算）・入社日・退職日・役職・保有資格・住所・連絡先・備考を管理。
    ここに登録した在職中の社員が、案件の担当者として選べる（「[社員マスタと担当者](#社員マスタと担当者)」参照）
  - 作業マスタ：明細で選べる作業・部品の名称と既定の単価・税率（管理番号順に並ぶ）
  - 社内規定：社内チャットが参照する文書
- ダッシュボード（`/`）：件数タイル4枚（顧客・車両・対応中の案件・車検切れ間近）＋
  売上の推移グラフ（直近6か月）＋案件ステータスのドーナツグラフ＋車検期限アラートを
  1画面に収めて表示（「[ダッシュボードの構成](#ダッシュボードの構成)」参照）
- 問い合わせフォーム（`/contact`。DBには保存せず、担当者へメール通知）
- プライバシーポリシー（`/privacy`）
- 店舗紹介ページ（`/lp`）：架空の店舗「バイクショップイケダ」のランディングページ
  （「[店舗紹介ページ（LP）](#店舗紹介ページlp)」参照）

各一覧画面には、キーワードでの絞り込みと並べ替えを用意しています（件数が多くない業務のため、
サーバーへ問い合わせ直さず画面側で処理しています）。また、顧客詳細・車両詳細・案件詳細からは
「＋」ボタンでその相手をあらかじめ選んだ状態の作成フォームを開けます。

顧客 → 車両 → 案件 → 見積・請求 → 明細項目、の順に親子関係を持つ構成です（削除すると
関連する子レコードも連鎖して削除されます）。データはPostgreSQLに保存されるため、
ログインできる人全員が同じ内容を見ます（会社設定のみadmin限定）。

## セットアップ

### 実行環境

このプロジェクトは **WSL2（Ubuntu）の中**で動かします。置き場所は次のとおりです。

| | 場所 |
| --- | --- |
| WSL から見たパス | `/home/tikeda/projects/shukudai2` |
| Windows から見たパス | `\\wsl.localhost\Ubuntu\home\tikeda\projects\shukudai2` |

VS Code は左下の緑のボタンから **「WSL に接続」** して開いてください。Windows 側の
`C:\...` に置いたまま WSL から操作すると極端に遅くなるため、作業は WSL 側に統一します。
ブラウザは Windows 側の Chrome や Edge をそのまま使えます（`http://localhost:5273` など）。

必要なものは次の3つです。

- WSL2（Ubuntu）と、WSL 統合を有効にした Docker Desktop
- Node.js 24 以上（`process.loadEnvFile` を使用しています）。`nvm install 24` で導入します
- pnpm（`corepack enable` で有効化）

新しいターミナルで `node` が見つからない場合は、`nvm use 24` を実行してください。

### 手順

```bash
pnpm install
cp .env.example .env          # DATABASE_URL に Neon の接続文字列を設定するなど、値を自分の環境に合わせて編集する
pnpm db:migrate               # テーブルを作成
pnpm db:seed                  # 動作確認用のダミーデータを投入（任意）
```

ローカルにPostgreSQLを別途起動する必要はありません（DBはNeonを使います）。

ログイン用のアカウントを発行します（自己登録は無効のため必須）。
パスワードは引数に書くとシェル履歴に残るため、`--password` を省略して対話入力にしてください。

```bash
pnpm user:create --email admin@example.com --name "管理者"
```

2人目以降は `--role user` を付けます。発行後に開発サーバーを起動します。

```bash
pnpm dev                      # http://localhost:5273
```

`pnpm dev` は本番と同じ **workerd**（Cloudflareのランタイム）上で動くため、環境差による事故が
起きにくくなっています。ローカルの Hyperdrive は接続先の指定が必要です
（「[環境変数・シークレット](#環境変数シークレット)」参照）。

## 現在の構成：Cloudflare Workers + Hyperdrive + Neon

```
利用者 → Cloudflare Workers（アプリ本体＋静的配信＋Basic認証）
              ↓ Hyperdrive（接続プール・接続確立の高速化）
           Neon（PostgreSQL）
```

Hyperdrive は Cloudflare 側にある中継役で、**ローカルには存在しません**。`pnpm dev` では
指定した接続先へ直接つなぐ代替動作になります（アプリの挙動は同じで、速度の効果だけが出ません）。

### なぜ Cloudflare Pages ではなく Workers なのか

課題の条件では公開先が **Cloudflare Pages** 指定でしたが、このアプリは **Cloudflare Workers**
で動かしています。理由を書いておきます。

Pages と Workers はどちらも Cloudflare が提供する無料のホスティング（インターネット上に
サイトを置く場所）ですが、役割が違います。**Pages は「出来上がったHTML・CSS・画像を配るのが主役」**、
**Workers は「プログラムを動かすのが主役」** です。

このアプリを Workers にした理由は2つあります。

1. **静的ファイルにも Basic認証をかけたかった**。Pages で認証を実装する場合は
   `functions/_middleware.ts`（リクエストが本体に届く前に必ず通る関所）を使いますが、
   Pages では **CSS・JS・画像はこの関所より手前で配信されます**。つまり画面には鍵がかかっても、
   ファイルのURLを直接叩けば誰でも中身を取れてしまいます。Workers なら
   `wrangler.jsonc` の `assets.run_worker_first` を有効にすることで、**全リクエストを
   認証に通した上で**静的ファイルを配れます（実際にこの取りこぼしを一度踏んで修正しました）。
2. **TanStack Start の Cloudflare 向けビルドが Workers を前提にしている**。
   `@cloudflare/vite-plugin` が出力するのは Workers 用の成果物で、Pages 用に組み直すと
   構成が遠回りになります。

なお、課題条件の「GitHubリポジトリを繋ぐ形で公開する」という点は満たしています。
`master` ブランチへ push すると Cloudflare 側でビルドとデプロイ（インターネット上のサーバーに
載せて公開すること）が自動で走ります（下記「デプロイ」参照）。

### 構成のポイント

- **ビルド**：[@cloudflare/vite-plugin](https://developers.cloudflare.com/workers/vite-plugin/) を
  `vite.config.ts` の**先頭**に置き、SSR環境を workerd で動かす。
- **エントリポイント**：Basic認証を挟むため、既定の `@tanstack/react-start/server-entry` ではなく
  [src/server.ts](src/server.ts) を使う（`wrangler.jsonc` の `main`）。
- **DB接続**：[src/lib/db.ts](src/lib/db.ts)。Hyperdrive の接続文字列はリクエストの `env` からしか
  取れないため、`src/server.ts` がリクエスト毎に DB 層へ渡す。
- **静的ファイル**：`dist/client` を Workers の Assets として配信する。ただし既定では
  静的ファイルが Worker より**手前**で配信され Basic認証を通らないため、
  `wrangler.jsonc` で `assets.run_worker_first` を有効にし、認証を通ったものだけを
  `ASSETS` バインディング経由で `src/server.ts` が返している。
  取得系（GET/HEAD）だけを対象にしているのは、静的配信側が他のメソッドに 405 を返し、
  そのまま返すとサーバー関数のPOSTが動かなくなるため。

### デプロイ

`master` へ push すると Cloudflare 側でビルドとデプロイが走ります（Workers Builds）。
設定は管理画面の Workers & Pages → shukudai2 → 設定 → ビルド から行います
（リポジトリには設定ファイルを置きません）。

| 項目 | 値 |
| --- | --- |
| ビルドコマンド | `pnpm run build` |
| デプロイコマンド | `pnpm exec wrangler deploy -c dist/server/wrangler.json` |
| ルートディレクトリ | `/` |

デプロイコマンドは既定値の `npx wrangler deploy` から**必ず変える**こと。理由は2つ。

- **`npx` が使えない**。`package.json` の `devEngines` が pnpm を必須にしているため、
  npm 経由で起動すると `EBADDEVENGINES` で落ちる。`pnpm exec` を使う。
- **設定ファイルの指定が要る**。ビルドすると `dist/server/wrangler.json` が生成され、
  デプロイはそちらを使う。省略するとルートの `wrangler.jsonc`（ビルド前のソースを指している）が
  読まれ、wrangler が `src/server.ts` を独自に再バンドルしてしまう。TanStack Start の
  コード変換（サーバー関数の抽出など）が抜け落ち、500エラーになる。

反映には数分かかります。すぐ反映したい場合や、GitHubを経由したくない場合は
`pnpm cf:deploy` を手で実行します。

### 環境変数・シークレット

秘密でない値は `wrangler.jsonc` の `vars`、秘密の値は `wrangler secret put <名前>` で登録します
（`nodejs_compat` により、どちらも `process.env` から読める＝[src/lib/env.ts](src/lib/env.ts) が
そのまま動きます）。値は zod スキーマで検証され、未設定・不正な形式ならその場で失敗します。
`env.ts` はサーバー側専用です。クライアントコンポーネントから import しないでください。

| 種別 | 変数 |
| --- | --- |
| vars（公開） | `BETTER_AUTH_URL` / `BASIC_AUTH_USER` / `SMTP_*` / `MAIL_FROM` / `CONTACT_NOTIFY_TO` |
| secret（非公開） | `BETTER_AUTH_SECRET` / `BASIC_AUTH_PASSWORD` / `DATABASE_URL` / `GEMINI_API_KEY` |

**設定ファイルが2つある点に注意**してください。読む相手が違います。

| ファイル | 読む相手 | 備考 |
| --- | --- | --- |
| `.dev.vars` | `pnpm dev`（Cloudflare版） | 本番のシークレットのローカル版 |
| `.env` | `pnpm dev:node` / `db:migrate` / `db:seed` / `pnpm test` / docker compose | 汎用 |

どちらも gitignore 済みです。**新しい秘密を足すときは両方に書く**こと。片方だけだと、
一方の環境でのみ動かないという分かりにくい形で表面化します（実際に `GEMINI_API_KEY` と
`BASIC_AUTH_PASSWORD` で2回踏んでいます）。

ローカルの Hyperdrive は接続先の指定が必要です。未指定だと `pnpm dev` が起動しません。

```bash
CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE="<DATABASE_URLと同じ値>" pnpm dev
```

#### 社内チャット（`GEMINI_API_KEY`）

未登録でもアプリは動きますが、社内チャットの画面で「社内チャットは未設定です」と表示されます。
使う場合は Google AI Studio（aistudio.google.com）でキーを発行し、次のコマンドで登録します。

```bash
pnpm exec wrangler secret put GEMINI_API_KEY   # 実行後に値の入力を求められる
```

キーは利用者ごとではなく**店舗で1つ**を管理者が登録します。社内規定は全員が同じものを読むため
個人差が無く、人数分の秘密を預かる必要も、個人の Google アカウントに費用を負わせる理由もありません。

登録すると Worker の新しいバージョンが自動で配信されるため、`pnpm cf:deploy` は要りません。
ローカルでも使う場合は `.dev.vars` に `GEMINI_API_KEY=<値>` を追記します。

### ハマった点

1. **モジュール読み込み時（グローバルスコープ）で乱数生成・通信をしてはいけない**
   Workers の制約で、`Disallowed operation called within global scope` エラーになる。
   better-auth の初期化（`betterAuth({...})`）と DB クライアントの生成がこれに該当したため、
   どちらも**最初に使われた時に生成する遅延初期化**へ変更した。呼び出し側を変えずに済むよう、
   `auth` と `db` は実体への Proxy として公開している
   （[auth.ts](src/lib/auth.ts) / [db.ts](src/lib/db.ts)）。
   なおローカル開発では requestごとにモジュールが評価されるためこのエラーが出ず、
   **本番だけ500になる**という形で表面化する。

2. **`betterAuth()` の戻り値型はファクトリ関数から推論する**
   `ReturnType<typeof betterAuth>` と書くとプラグイン（admin/username）由来のAPIの型が失われ、
   `createUser` や `role` が「存在しない」と型エラーになる。

### この構成での制約

- **メール送信は動かない**：Workers では nodemailer（SMTP）が使えない。`SMTP_*` はダミー値を
  設定してあり、問い合わせフォームを送信すると画面に「送信に失敗しました」と表示される。
  対応する場合は Resend など HTTP API 型のサービスへ差し替える。
- **`pnpm user:create` / `pnpm auth:schema`（better-auth CLI）は Node 上で動く**。
  DB接続は `.env` の `DATABASE_URL`（Neonへの直接接続）を使うため、そのまま利用できる。

## データベース

### スキーマを変更する手順

`src/db/schema.ts` を変えたときは、**push の前に**手元でマイグレーションを適用します。
自動デプロイはコードだけを反映し、DBの構造は変えないためです。

```bash
# 1. src/db/schema.ts を編集
pnpm db:generate   # 2. マイグレーションSQLを生成
#    ← 3. 生成されたSQLを必ず目で確認する（下記）
pnpm db:migrate    # 4. Neonに適用
git push           # 5. コミットしてpush（自動デプロイが走る）
```

**手順3を省かないこと。** drizzle-kit が生成するSQLは、既存データを考慮しません。

| 変更の種類 | 生成SQLの安全性 |
| --- | --- |
| 新しいテーブルを追加 | **安全**。中身が空なので `CREATE TABLE` が通る |
| 任意の列を追加 | 安全 |
| **既存テーブルに必須（NOT NULL）の列を追加** | **そのままでは必ず失敗する** |

最後のケースでは「列を追加 → 既存行に値を入れる → NOT NULL化 → 一意制約」の順に
手で分ける必要があります。実例が
[0017_light_skrulls.sql](src/db/migrations/0017_light_skrulls.sql)（作業マスタへの管理番号追加）
にあるので参考にしてください。

既存機能への影響も種類によって違います。新しいテーブルの追加は、古いコードがそのテーブルを
知らないため既存画面を壊しません。一方、既存テーブルへの必須列の追加は、デプロイが済むまで
その画面の新規登録が失敗します。

### ローカルと本番は同じDBを共有している

ローカルの開発環境もCloudflare Workers（本番）も、**同じNeonのDBを指しています**
（本番はHyperdrive経由、ローカルは`.env`の`DATABASE_URL`経由ですが、接続先のDBは同一）。
同期しているのではなく、そもそもDBが1つしかない、というのが正確な理解です。

| 変更の種類 | ローカルで変更した場合 | 本番で変更した場合 |
| --- | --- | --- |
| データ（顧客を1件追加など） | 本番にも即反映 | ローカルにも即反映 |
| DBの構造（`pnpm db:migrate`） | 本番にも即反映 | 同上 |
| 画面・コード | **反映されない**（デプロイが必要） | （本番でコードは直接編集しない） |

この構成は「ローカルでの試行錯誤が本番データを直接壊しうる」という裏返しでもあります。
分けたい場合はNeonのブランチ機能で開発用DBを作ります。

### Neonを選んでいる理由

このアプリは「普通のPostgreSQL + drizzle-orm + better-auth」という一般的な構成で、
Neon固有の機能は使っていません。そのため**標準的なPostgreSQLサービスなら`DATABASE_URL`の
差し替えだけで移行できます**。それでもNeonを維持しているのは以下の理由です。

- すでに動いており、乗り換えには必ず事故のリスクが伴う（実際にsearch_pathの件で一度ハマっている）
- 無料枠（ストレージ0.5GB／コンピュート100CU時間）に対し、この規模の使用量は極小
- 開発用DBを分けたくなった時に、ブランチ機能がそのまま使える
- Cloudflare Workersへ移る可能性を残せる（HTTP経由の接続に対応しているのはNeonの強み）

| ケース | 候補 | 備考 |
| --- | --- | --- |
| 今のまま安定運用したい | **Neon（現状維持）** | 移行の手間ゼロ |
| 将来ファイル保存や別の認証機能も使いたい | Supabase | PostgreSQLなので差し替えのみ |
| Cloudflareに全部寄せたい | Cloudflare D1 | **SQLite系で別物**。スキーマ・認証基盤の作り直しが必要 |

**接続文字列は「直接接続」を使うこと。** Neonにはホスト名に`-pooler`が付いたプーラー経由の
URLもありますが、データ移行時に`pg_dump`が出す
`SELECT pg_catalog.set_config('search_path', '', false)`をプーラー経由で実行してしまい、
使い回される接続の`search_path`が空のまま壊れてテーブルが見えなくなる不具合を踏んでいます
（`ALTER DATABASE ... SET search_path`をやり直しても、既に壊れたプール済み接続には反映されない）。
永続接続するサーバーではプーラーのメリットがなく、事故の元になります。

### pgAdminでNeonのデータを見る

DBの中身をブラウザで確認したいときは pgAdmin を使います（この用途のためだけにコンテナを
起動したままにしています）。

```bash
docker compose up -d pgadmin   # http://localhost:5051
docker compose stop            # 使い終わったら停止
```

1. 左「Servers」を右クリック →「登録」→「サーバー」
2. 「全般」タブ：名前に`Neon`など分かりやすいものを入力
3. 「接続」タブに以下を入力

   | 項目 | 値 |
   | --- | --- |
   | ホスト名/アドレス | `.env`の`DATABASE_URL`のホスト部分（`@`の後ろ、`/neondb`の手前） |
   | ポート | `5432` |
   | メンテナンスDB | `neondb` |
   | ユーザー名 | `neondb_owner` |
   | パスワード | `.env`の`DATABASE_URL`の`neondb_owner:`の直後の文字列 |

4. 「SSL」タブ：「SSL mode」を`Require`に変更（Neonは暗号化接続が必須）

ローカルの`postgres`サービスは通常起動していないため、ホスト名`postgres`で登録した古い
サーバーは`failed to resolve host 'postgres'`になります。使わないなら削除して構いません。

## 画面と設計の方針

### 画面デザインの方針

管理画面は**明るいテーマ＋オレンジのアクセント**、店舗紹介ページ（LP）だけは**別の配色**です。
管理画面は長時間の入力作業で使うため見やすさを優先しています。

- **配色は[app.css](src/styles/app.css)の`@theme`に集約**。`shell`（最も奥の背景）／`surface`（カード）／
  `surface-raised`（ホバー・入れ子）／`line`（罫線）／`ink`系（文字）／`accent`（オレンジ）／
  `danger`・`success`・`info`（状態）という**役割で名前を付けている**ため、配色を変えたい時は
  このファイルだけを直せば全画面に反映されます。
  画面側では`bg-surface`・`text-ink-muted`のように役割名で参照し、`slate-700`のような具体色は書きません。
  エラー表示も`text-red-400`ではなく`text-danger`と書きます。
- **配色の切り替えはクラスひとつ**。`.theme-lp` は`@theme`の変数を再定義するだけなので、
  画面側のクラス（`bg-surface`など）は書き換え不要です。LP・プライバシーポリシー・
  問い合わせフォームが最上位の`<div>`にこれを付けています。
  **状態色（`danger`/`success`/`info`）も忘れず再定義すること**。既定のままだと暗い地の上で
  エラー表示が読めません（実際に問い合わせフォームで踏みました）。
- **アクセント（オレンジ）は「今いちばん押してほしいもの」にだけ使う**。主操作ボタン、選択中のナビ、
  税込合計、作業中ステータスなど。多用すると効かなくなるため、副操作は`outline`／`ghost`にしています。
- **メリハリの付け方**。平坦に見えないよう、次の3つを意図的に使い分けています。
  - **大きさの差をはっきり付ける**：画面見出しは`text-3xl font-black`、ダッシュボードは`text-4xl`。
    中間の太さ（`font-medium`）を減らし、太い／細いの2段階に寄せています。
  - **面で示す**：選択中のナビとダッシュボードの主要数値は、薄い色違いではなくオレンジで塗りつぶします。
    一覧の行はホバー時に左端へオレンジの縦線が伸び、いま見ている行が分かります。
  - **区切りを作る**：見出しの下に罫線、カードの見出し帯に薄い背景、カードにはごく弱い影。
- **全画面共通のナビ**（[layout.tsx](src/components/ui/layout.tsx)の`AppShell`）で、どの画面からでも
  顧客・車両・案件・見積請求へ移動できます。左に固定サイドバー・右に本体という構成で、
  狭い画面（1024px未満）では上部に移り、スマホでは「店名＋ログアウト」と「メニュー」の
  2段に分かれます（1行に詰め込むとメニューがほとんど見えなくなるため）。
- **状態は文字ではなく色付きバッジで示す**。案件ステータス（未作業＝無彩色／作業中＝オレンジ／
  完了済み＝緑）、見積書＝青・請求書＝オレンジ。
- **金額・数量は`tabular-nums`で桁を揃える**。一覧で縦に並んだ時に読み違えないようにするためです。

### スマホでの表示

PCの画面をそのまま縮めるのではなく、**幅768px（Tailwindの `md`）を境に組み方そのものを
切り替えています**。横スクロールしないと読めない画面は、スマホでは使えないためです。

| 部品 | 広い画面（768px以上） | スマホ（768px未満） |
| --- | --- | --- |
| 一覧（`DataTable`） | 列で揃えた表 | 1件＝1枚のカード。先頭の列が見出し、残りは「項目名｜値」、操作ボタンはカード下部 |
| 基本情報（`DetailList`） | ラベル｜値を横に並べた表 | ラベルの下に値を置く縦積み |
| ナビ（`AppShell`） | 左の固定サイドバー | 上部2段（店名＋ログアウト／メニュー） |
| 絞り込み（`ListToolbar`） | 検索欄と並べ替えを横並び | 検索欄だけで1行を使う |
| 見出し・カードの操作ボタン | 横一列 | 入らなければ折り返す（`flex-wrap`） |
| 帳票の印刷画面 | A4幅（210mm）で表示 | 帳票だけを横スクロールの箱に入れ、ページ全体は動かさない |

両方のHTMLを出して `hidden` / `md:hidden` で出し分けています（JavaScriptで画面幅を測って
切り替えるのではないため、最初の表示から正しい形で出ます）。

画面の高さは `h-screen`（100vh）ではなく **`h-dvh`** を使っています。スマホのブラウザは
アドレスバーの出し入れで表示領域が伸び縮みしますが、100vh はいちばん高い状態で固定される
ため、下端のボタンや一覧の最終行が画面の外に隠れてしまうためです。

### ダッシュボードの構成

来店対応の合間に開くことを想定し、**スクロールせず1画面で全体を見渡せる**ことを優先しています。

```
┌ 顧客 ─┬ 車両 ─┬ 対応中の案件 ─┬ 車検切れ間近 ┐   ← 件数タイル4枚
├───────┴───────┴─────────────┴────────────┤
│ 売上の推移（直近6か月）  │ 案件の状況 │ 車検期限が近い車両 │
│ 請求金額／見積金額＋グラフ │ ドーナツ  │ 先頭3台            │
└──────────────────────┴──────────┴──────────────────┘
```

- **グラフはライブラリを使わず、SVGを自前で描いています**（[chart.tsx](src/components/ui/chart.tsx)）。
  Cloudflare Workers にはスクリプトサイズの上限があり、この程度の表現のために
  数十KBの依存を足したくないためです。色は`app.css`の`@theme`変数を直接参照しているので、
  配色を変えるとグラフも一緒に変わります。
- **タイルの並びは「規模 → 要対応」の順**。車検切れ間近は0台なら通常表示、
  1台でもあれば数字を赤くして目に留まるようにしています。
- **車検アラートは先頭3台だけ**を出し、残りは件数で示して「車両一覧へ」に送ります。
- 月別売上は、売上の無い月も0として並べます（[dashboard-series.ts](src/lib/dashboard-series.ts)）。
  DBは売上のあった月しか返さず、そのままだと空白の月が詰められて
  「毎月売上がある」ように見えてしまうためです。

### 一覧画面の表示

顧客・車両・案件・見積請求の一覧は、**項目ごとに列を分けた表**（`DataTable`）で出しています。
1行にまとめて書くより、列で揃っているほうが同じ項目を縦に見比べられるためです。
**詳細画面の中にある小さな一覧（保有車両・関連案件・見積請求・明細項目・社員マスタ）も
同じ `DataTable` で列分けしています**。

| 画面 | 列 |
|---|---|
| 顧客 | 顧客名（担当者名）／保有台数／電話番号／メール／住所 |
| 車両 | モデル名（車両番号）／メーカー／所有者／案件／車検期限 |
| 案件 | **番号**／案件名／ステータス／顧客・車両／担当者／作業予定／請求 |
| 見積・請求 | 種別／番号／タイトル／顧客・車両／金額（税込）／発行日 |

- **列見出しは `sticky` でカードの中に貼り付け**ています。中身だけがスクロールするので、
  下まで見ても「どの列が何か」が分からなくなりません。
- **列幅は指定せず、ブラウザの自動配分に任せています**。特定の列に `w-full` を付けると
  その列が余白を全部吸ってしまい、名前が短いときに大きな空白ができて不格好になりました。
  潰れると困る列にだけ `min-w-[10rem]` のように下限を決めています。
- **表の中だけ本文より一段小さい文字**（13px）にして、列が多くても収まるようにしています。
- **スマホ（768px未満）では、表をやめて1件1枚のカードに切り替えます**
  （「[スマホでの表示](#スマホでの表示)」参照）。
- 車検期限は、60日以内なら赤太字にして案内漏れに気づけるようにしています。
- **本文の横幅には上限を付けていません**（`max-w-none`）。上限を上げても広い画面では
  余白ばかり目立ったため、上限そのものを外しました。
- **`DetailList`（基本情報）も見た目を`DataTable`に揃え、ラベル｜値の表**として描画します。
  短い項目は無理に1行1項目にせず、横に並べて「通常の項目全体が2段に収まる」ように組みます
  （1行に並べる組数は項目数に応じて自動、上限4組）。`wide`を付けた項目（住所・備考など
  長文になりうるもの）だけ単独で1行にします。
  **表に`w-full`は付けていません**。付けると値の列に余った幅が押し付けられ、短い値の右側にだけ
  大きな空白ができてしまうためです。

### 番号（連番）の持ち方

顧客・車両・案件・見積請求は、**それぞれ一意な番号**を持ちます。主キーはUUIDですが、
UUIDは電話口で読み上げたり書類に書いたりできないため、人が扱う番号を別に持たせています。

| 対象 | 列 | 画面での呼び方 |
|---|---|---|
| 顧客 | `customers.customer_number` | 番号 |
| 車両 | `vehicles.manage_number` | 管理番号 |
| 案件 | `cases.case_number` | 番号 |
| 見積・請求 | `quotes.doc_number` | 番号 |
| 社員（マスタ） | `staff_profiles.staff_code` | 社員コード |
| 作業マスタ | `work_items.code` | 管理番号 |

- いずれも `serial`（自動採番）＋ `unique` 制約付きです。**採番と一意性をDBに任せる**ため、
  アプリ側で「次の番号」を数える必要がなく、同時に登録しても重複しません。
- 車両だけ `manage_number` という名前なのは、**`vehicle_number`（ナンバープレートの番号）が
  既にある**ためです。画面でも「管理番号」と「車両番号」で呼び分けています。
- 社員コードだけは、better-auth が発行する文字列IDが主キーのため `staff_profiles` 側に持ちます。
  詳細情報が未入力でもコードは振られるよう、**アカウント作成時に空の詳細行を必ず作って**います。
- **作業マスタの管理番号だけは手入力**（3桁）です。並び順も兼ねており、
  100番台=工賃、200番台=部品、900番台=割引・査定として、割引が一覧の下に来るようにしています。
- 画面では6桁ゼロ埋め（`000123`）で表示し、一覧の先頭列に置いています。

### 社員マスタと担当者

社員マスタは**ログインアカウントそのもの**です。ここに登録した人が、そのまま案件の担当者として
選べます。以前は「社員マスタ」と「担当者マスタ」を分けていましたが、同じ人を二重に登録する
手間しか生まなかったため統合しました。

- **案件は担当者の「名前」を保存**しており、社員マスタとは外部キーで結んでいません。
  退職や削除があっても、過去の案件に記録された担当者名を変えないためです。
- **退職日を入れた社員は、担当者の選択肢から外れます**。ただし過去の案件に残った名前はそのままで、
  その案件を編集したときも担当者が黙って空にならないよう、選択肢に
  「◯◯（社員マスタにありません）」として残します。
- 退職は在職フラグではなく**退職日**で持っています。「いつ辞めたか」も残したいためです。
- **年齢は保存せず、生年月日から表示のたびに計算**します（[staff.ts](src/lib/staff.ts)）。

**ログインしない社員も登録できます。** 社員マスタは `user` テーブルそのものですが、
パスワードなどの認証情報は別テーブル（`account`）に入るためです。アルバイトなど、
作業の担当にはなるがシステムを使わない人を名簿に載せられます。一覧には「ログイン不可」と
表示され、編集画面でパスワードを設定するとそのままログインできるようになります。

**個人情報の扱い**：社員の詳細情報には氏名・生年月日・住所・電話番号が入ります。

- 閲覧・編集できるのは **admin権限のみ**です（案件の担当者選択で使う「名前」だけは、
  一般ユーザーも取得できる別の関数から返しています）。
- 設定画面は `beforeLoad` でも admin を確認しており、**画面の読み込みが始まる前に**
  一般ユーザーをダッシュボードへ戻します。入口で止めたほうが情報が一瞬でも表示される余地が
  なくなるためです。
- 詳細情報は better-auth が生成する `user` テーブルではなく、**別テーブル
  （`staff_profiles`）に分けています**。`user` テーブルは認証設定を変えるとCLIで作り直されるため、
  業務で使う項目をそこに足すと消えてしまうからです。
- **この練習用アプリには実在の従業員の情報を入れないでください。** 投入済みのデータは
  すべて架空のものです。

### マスタ管理の配置

設定（旧マスタ）は、以前はダッシュボード最下部のリンクからしか開けませんでした。
これだと会社設定を直して帳票を確認する、といった往復がしづらいため、**ナビに常設**しています。

- 顧客・車両・案件・見積請求は、実際の仕事の流れそのままの並びで「毎日使う業務」
- 設定は「たまにしか使わない、自分と店舗の設定」

という役割の違いを、ナビ上の位置と区切り線で表現しています。admin以外のユーザーには
「ログアウト」しか出ないため、権限による見え方の違いも自然に表現されます。

### 見積書・請求書のPDF出力

`/quotes/$id/print` が帳票の印刷ページです。見積・請求の一覧・詳細にある「印刷 / PDF」ボタンから開き、
**ブラウザの印刷画面で「送信先」を「PDFに保存」にするとPDFファイルとして保存できます**。

[quote-document.tsx](src/components/documents/quote-document.tsx) が帳票のテンプレートです。
元のFileMaker「見積・請求_印刷」レイアウトの構成（発行元ヘッダ → 宛名 → 合計金額 → 明細表 →
振込先 → 通信欄）を踏襲しています。

- **差し込む内容はすべてDBから**。発行元は会社設定、宛名は顧客、明細は見積・請求の明細項目を
  使います。テンプレートを直さなくても、会社設定を変えれば全帳票の印字内容が変わります。
- **種別で文言を出し分ける**。見積書は「お見積もり内容は以下になります」「御見積金額」、
  請求書は「下記の通りご請求申し上げます」「御請求金額」。**振込先は請求書のときだけ**印字します。
- **書類番号は`quotes.doc_number`（連番）**。UUIDは人が読み上げられないためです。
- 画面全体は明るいテーマですが、**帳票は紙に出す前提で白地・黒文字**にしています。

**PDF生成にライブラリを使っていない理由**：日本語のPDFを自前で生成するにはCJKフォントの
埋め込みが必要で、フォントファイルだけで数MB〜十数MBになります。Cloudflare Workers には
スクリプトサイズの上限があるため現実的ではありません。ブラウザの印刷機能を使えば、
フォントは閲覧者の端末のものが使われるためこの問題が起きません（元のFileMakerも
「印刷レイアウトに切り替えてPDF保存」という同じ考え方でした）。
用紙サイズ・余白は[app.css](src/styles/app.css)の`@page`で指定しています。

### 店舗紹介ページ（LP）

`/lp` は、来店前のお客様に見せることを想定した集客用のページです。**掲載している店名・住所・
電話番号・料金・お客様の声はすべて架空のダミー**で、実在の店舗や個人とは関係ありません。

- **デザインは [design-spec.yml](design-spec.yml) に従っています**。配色（深緑・焦げ茶・生成り）、
  ウェイト400で字間を詰めた見出し、角を落とさないカード、高さ58pxの丸ボタンなどはすべて
  この仕様に由来します。元になったカンプは `docs/design-reference/` にあり、YAMLだけでは
  分からない文字組み（表の中央揃え、見出しと本文の段違いなど）の確認に使えます。
- 仕様は home / pricing / services の3ページ構成ですが、このページは**1枚に統合**しています。
- 管理画面向けのナビ（`AppShell`）は使わず、[lp.tsx](src/routes/lp.tsx)だけで完結させています。
- **写真は `public/lp/` に置き、`PHOTOS` の表で差し替えます**。`src` が空の枠は、CSSで作った
  代替の面を同じ大きさで表示するため、写真が揃っていなくても版面は崩れません。
- **料金は作業マスタの単価を税込に直した値**です。どのマスタ由来かをコメントで残しているので、
  単価を変えたときに追随できます。
- ダッシュボードからは**別ウィンドウ（新しいタブ）で開きます**。
- LPも他の画面と同じく**Basic認証の内側**にあります。一般公開したい場合は
  [server.ts](src/server.ts)の`isAuthorized`で`/lp`を除外しますが、`noindex`のまま公開される点に
  注意してください。

## 実装上の注意点

- **ログインの判定はサーバー側で行う**。[authGuard.ts](src/server/authGuard.ts) の `requireSession()`
  （ログイン必須）／`requireAdminSession()`（admin必須）を各サーバー関数の先頭で呼び、条件を満たさなければ
  `/login` または `/` へリダイレクトします。画面側の表示制御だけに頼っていません。
- **消費税は税率ごとに税抜小計をまとめてから、1回だけ丸める**。元のFileMakerは行ごとに
  丸めており、数量が2以上のとき「税抜合計＋消費税額」が税込合計と一致しない不具合があったため、
  そのまま移植していません。計算ロジックは[quote-summary.ts](src/lib/quote-summary.ts)に分離し、
  [quote-summary.test.ts](tests/quote-summary.test.ts)で端数処理を検証しています。
- **社内チャットのプロンプトは system_instruction に置く**。質問と同じテキストに混ぜると、
  質問文に紛れ込ませた指示（プロンプトインジェクション）でルールを上書きされやすくなります。
  回答は登録された社内規定だけを根拠にするよう指示しています（[chat.ts](src/server/chat.ts)）。
- pnpm 12.3.4 は `@tanstack/start-server-core` が使う npm エイリアス依存 `h3-v2`（= `h3`）を
  再解決できず、依存を追加しようとすると 404 で失敗します。[pnpm-workspace.yaml](pnpm-workspace.yaml)
  の `overrides` で解決先を明示して回避しています。この行を消すと `pnpm add` が通らなくなります。
- **`vite.config.ts` で `server.host: true` を指定しています**。WSL の中で既定の localhost
  だけを見て待ち受けると、環境によっては Windows のブラウザから届かないことがあるためです。
- **データベースは他プロジェクトと共有していません**。`docker-compose.yml` の `name:` により、
  コンテナ・データ保管庫・ネットワークがこのプロジェクト専用に分かれます。
- **社員マスタの更新で、アカウント名（`username`）が変わっていない場合は更新データに含めない**
  （[accounts.ts](src/server/accounts.ts) の `updateAccount`）。better-authの`username`プラグインは
  「自分以外のユーザーを、既存のアカウント名のまま更新する」際に、更新対象と操作者（管理者）のIDを
  取り違えて誤って「アカウント名が既に使われています」と判定することがあるためです。
- **`server.mjs` はアプリ本体を動的importで読み込む**（Node向けビルドの場合）。アプリは
  読み込んだ時点で環境変数を検証するため、静的importにすると `.env` の読み込みより先に評価されて
  起動に失敗します。

## 実装上の落とし穴（CRUDで実際に踏んだもの）

新規・更新・削除まわりで実際に不具合が出た点です。同じ種類のミスを繰り返さないために残します。

### 1. 任意項目を空にしても値が消えない

zodの正規化で空文字を `undefined` にしていたところ、**drizzle-orm の `.set()` は
値が `undefined` のキーをSQLから除外する**ため、更新時にその列が一切書き換わりませんでした。
「案件の担当者を未定に戻せない」「退職日を消して在職中に戻せない」という形で表面化します。

**対策**：`optionalText` / `optionalDate` / `optionalInt` は `undefined` ではなく **`null`** を返します
（[validation.ts](src/lib/validation.ts)）。`tests/validation-optional.test.ts` で固定しています。

### 2. モーダルを閉じても中身がDOMに残り、前の行の値が保存される

ark-ui の `Dialog` は既定で**閉じても中身をアンマウントしません**。フォームは `defaultValue` を使う
非制御コンポーネントなので、一度マウントされると後から `defaultValue` を変えても表示は変わりません。
その結果、**別の行の「編集」を開いても前回の値が残り、そのまま保存**されてしまいます。
セレクト（所有者・ステータス・権限）で起きると、気づかないままデータが書き換わります。

**対策**：[form.tsx](src/components/ui/form.tsx) の `Modal` に `lazyMount unmountOnExit` を付けています。
非制御フォームをモーダルで使う場合は必ずセットで考えること。

### 3. `<select>` に空の選択肢が無いと、未指定でも先頭が保存される

`defaultValue=""` を渡しても、一致する `<option>` が無ければブラウザは先頭を選びます。
車両のメーカー・色が、未指定のつもりでも必ず「ホンダ」「ブラック」になっていました。

**対策**：任意の選択項目には `{ value: "", label: "未選択" }` を先頭に入れます。
なお `SelectField` は当初エラー文言を描画しておらず、未選択のまま送信してもメッセージが
出ない状態でした（問い合わせフォームで発覚）。`TextField` と同じく `invalid`/`error` を渡します。

### 4. 「1画面に収める」ための高さの持ち方

一覧画面は、**ページ全体をスクロールさせず、一覧の中身だけをスクロール**させています。
こうすると見出し・検索欄・件数表示が常に見えたまま、画面内に収まります。

- `AppShell` の一番外側を `h-screen overflow-hidden` にして、画面の高さに固定
- 一覧画面は `<AppShell fill>` と `<Card fill>` を**セットで**使う

**見出しや絞り込みを「構造的にスクロール領域の外側」へ置くことが要点**です。
はじめは本文ごとスクロールさせたうえで高さ計算で収めようとしましたが、
計算が少しでも狂うと見出しごと動いてしまいました。

- **`min-h-0` を付ける**。flexの子は既定で中身より小さくならないため、これが無いと
  カードが縮まず画面の外へあふれます。
- **パーセントの高さ（`min-h-full` / `h-full`）に頼らない**。「親の高さが確定していること」が
  条件で、条件が崩れると子が高さいっぱいに広がらず、結局ページ全体がスクロールしてしまいます。

### 5. 固定表示（sticky）と重なり順

`position: sticky` を使うと重なり順の指定が必要になるため、次の順に揃えています。

| 要素 | z-index | 理由 |
|---|---|---|
| 一覧の見出しバー | 20 | 一覧の行より前に出す |
| 上部ナビ（狭い画面のみ） | 30 | 見出しバーより前に出す |
| モーダルの背景 | 40 | 固定表示のものをすべて覆う |
| モーダル本体 | 50 | 最前面 |

モーダルは `z-index` を指定しないと **固定表示の見出しバーの後ろに隠れます**
（ark-ui は見た目を持たないヘッドレスUIで、既定の `z-index` が無いため）。

## 外部システムからのログイン確認（社内ダッシュボード連携）

社内ダッシュボードなど別システムがこのアプリのログイン状態を確認したい場合、`account` テーブルの
パスワードハッシュに直接クエリするのではなく、better-auth が標準で提供する
`GET /api/auth/get-session`（`src/routes/api/auth/$.ts` 経由。追加実装は不要）を使ってください。
未ログイン・無効なセッションなら `null`、有効なら `{ session, user }` をJSONで返し、
`user` にはパスワード関連の情報は一切含まれません。

呼び出し元が別オリジンのブラウザアプリになる場合は、`src/lib/auth.ts` に `trustedOrigins` の設定と、
Cookieをサブドメイン間で共有するための設定が別途必要です。社内ダッシュボードのURLが
決まっていないため、現時点では未設定です。

## 過去の構成（参考）

現在は使っていませんが、戻せるようリポジトリに残している構成です。

### Docker でアプリまで動かす

アプリ本体をこのPCのDockerで動かす構成です（DBはNeonのまま）。

```bash
docker compose --profile rollback up -d postgres  # ローカルDBも使う場合
pnpm build:node                                    # Node向けにビルド
docker compose up -d --build                       # app + nginx + mailserver + pgadmin + cloudflared
```

`http://localhost:8080`（`.env` の `NGINX_PORT` で変更可）で開きます。
アプリコンテナ自体はホストへ直接公開せず、**nginx経由でのみ**アクセスする構成です
（直接ポートを公開すると、`BETTER_AUTH_URL` とHostヘッダがずれてCSRF検証に失敗するため）。
初回はマイグレーションとアカウント発行をコンテナ側で実行します。

```bash
docker compose exec app pnpm db:migrate
docker compose exec app pnpm user:create --email admin@example.com --name "管理者"
```

停止は `docker compose down`、**DBの中身ごと消す場合のみ** `docker compose down -v` です。

注意点がいくつかあります。

- **nginxは`.env`の`BASIC_AUTH_USER`/`BASIC_AUTH_PASSWORD`が未設定だと起動に失敗します**。
  ID/パスワードはコンテナ起動時に [generate-htpasswd.sh](nginx/generate-htpasswd.sh) が
  `.env` から生成します（値をイメージやコードに焼き込まないため）。
- **nginxは `Host` ヘッダを `$host` ではなく `$http_host` で転送しています**。`$host` はポート番号を
  含まないため、`BETTER_AUTH_URL`（ポート込み）と不一致になり、サーバー関数のCSRF検証が403になります。
- **docker-mailserverは最低1つメールアカウントを作成しないと起動が完了しません**
  （約2分でDovecotの起動待ちを諦めてコンテナが不健全になります）。

  ```bash
  docker compose exec mailserver setup email add no-reply@shukudai2.local "任意のパスワード"
  ```

- **docker-mailserverは社内限定の送信専用リレー**として最小構成にしており（SpamAssassin・
  ClamAV・fail2ban はすべて無効）、TLS証明書やDNSのSPF/DKIM/PTR設定は行っていません。
  実際にGmail宛へ送信テストしたところ、DMARCポリシー違反で拒否されました
  （`550 5.7.26 Unauthenticated email ... is not accepted due to domain's DMARC policy`）。
  社外へ配信する必要が出た場合は、SendGrid・Amazon SES・Postmark などの利用を検討してください。
- **コンテナのタイムゾーンを `Asia/Tokyo` に固定しています**。日付項目の初期値がサーバーと
  ブラウザでずれないようにするためです。alpine は `tzdata` を入れないと `TZ` が無視されます。

この構成でのみ使う環境変数は次のとおりです（`.env` に置きます）。

| 変数 | 用途 |
| --- | --- |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` / `POSTGRES_PORT` | ロールバック用のローカルpostgres（`profiles: [rollback]`）の設定 |
| `NGINX_PORT` | nginxのホスト側公開ポート（既定 8080） |
| `PGADMIN_DEFAULT_EMAIL` / `PGADMIN_DEFAULT_PASSWORD` / `PGADMIN_PORT` | pgAdmin のログイン情報と公開ポート |
| `SMTP_*` / `MAIL_FROM` / `CONTACT_NOTIFY_TO` | 問い合わせ通知メールの設定 |
| `MAIL_DOMAIN` / `MAIL_SMTP_PORT` | docker-mailserver のドメイン名と公開ポート |
| `TUNNEL_PUBLIC_URL` | Cloudflare Tunnel の公開URL。設定すると`BETTER_AUTH_URL`を上書きする |

`POSTGRES_PASSWORD` は `DATABASE_URL` に埋め込むため、`@` `:` `/` を含めず英数字のみにしてください。

### Cloudflare Tunnel（一時的な外部公開）

`cloudflared` サービスが Quick Tunnel（アカウント登録不要）を使い、
`https://xxxx.trycloudflare.com` のようなURLで一時的な外部アクセスを可能にします。
起動のたびにURLが変わるため、社内での動作確認・共有用と割り切ってください。

発行されたURLを `.env` の `TUNNEL_PUBLIC_URL` に設定し、`app` コンテナを再起動します
（設定しないと外部URLとOriginがずれてログインが403になります）。

**現在は使っていません。** アプリ自体がCloudflare上で動いているため、トンネルを掘る相手が
いないためです。恒常的に独自ドメインで公開したい場合は Quick Tunnel ではなく
[named tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/) を使います。

### Railway（廃止済み）

アプリ本体を Railway（Dockerイメージをそのままデプロイできるホスティング）で動かしていた時期が
あります。**Cloudflare Workers への移行後、サービスごと削除済み**です。

移行の決め手は**費用**でした。Railwayは従量課金で使うほど増える一方、Cloudflare Workersは
この規模なら無料枠に収まります。長期間動かし続ける前提のため移行しました。

事前の見積もりと実際の差を記録しておきます。

| 事前の見積もり | 実際 |
| --- | --- |
| `postgres`パッケージ（TCP接続）は動かないので`@neondatabase/serverless`へ差し替えが必要 | **不要だった**。Hyperdrive + `nodejs_compat` により `postgres` パッケージのまま動いた |
| better-auth（`node:crypto`依存）の調整が必要 | ライブラリ自体は動いた。ただし**初期化タイミング**の修正が必要だった |
| メール送信（nodemailer）が使えない | そのとおり。ダミー設定のまま保留 |
| ビルド構成の変更が必要 | `@cloudflare/vite-plugin`を足すだけで済んだ |

一方、**事前に見積もれていなかった問題**が2つあり、こちらの方が時間を使いました。どちらも
「[現在の構成](#現在の構成cloudflare-workers--hyperdrive--neon)」の節に詳しく書いてあります。

1. `wrangler deploy` にビルド出力側の設定を渡さないと、ソースが再バンドルされて500になる
2. Workers はモジュール読み込み時の乱数生成・通信を禁止しており、better-authとDB接続の
   初期化を遅延化する必要があった（**ローカルでは再現せず本番だけ500になる**）

   認証まわりはそのまま引き継いでいる。
5. **帳票とFileMaker機能差の解消** — 見積書・請求書のPDF出力、明細ごとの消費税率、
   見積→請求のワンクリック変換、各一覧の絞り込み・並べ替え、郵便番号からの住所自動入力、
   車検期限アラートなどを追加した。
6. **画面の作り直し** — ダークテーマから明るいテーマへ変更（LPのみ暗いまま）、
   左サイドバー化、一覧を1画面に収める構成、`DataTable` による列分割、見出しの体裁統一。
   ダッシュボードはカード＋グラフ構成に刷新した。
7. **CRUD全体の監査** — 「担当者を変更しても表示が変わらない」という報告をきっかけに全画面を
   点検し、任意項目・モーダル・セレクト・削除範囲に関する不具合をまとめて修正した
   （「[実装上の落とし穴](#実装上の落とし穴crudで実際に踏んだもの)」参照）。
8. **社員マスタへの統合** — 担当者マスタを廃止して社員マスタ（ログインアカウント）に一本化し、
   社員の詳細情報（`staff_profiles`）を追加した。
9. **お客様向けページと社内チャット** — 店舗紹介ページ（LP）を追加し、その後
   `design-spec.yml` に沿って全面的に作り直した。プライバシーポリシーを新設し、
   問い合わせフォームの配色をLPに合わせ、件名を選択式に変更。社内規定を参照して答える
   社内チャット（Gemini API）を追加した。
10. **作業マスタの整備と自動デプロイ** — 作業マスタに管理番号を追加して並び順を整理し、
    LPの料金表示をマスタの税込換算にそろえた。静的ファイルがBasic認証を素通りしていた
    不具合を修正し、GitHubへのpushで自動デプロイされるよう Workers Builds を設定した。

## どう AI に頼んだか

このアプリは、ほぼ全編を **Claude Code**（ターミナルで動く対話型のAI開発ツール）に指示を出して
作りました。私自身は FileMaker での業務アプリ作成には慣れていますが、Web の用語はほとんど
知らない状態から始めています。

### 頼み方の基本方針

最初にこの3つを AI に伝えました。この3つは、以降ずっと効き続けました。

1. **「実装はまだしなくてよいので、まず全体構成を教えて」** と段階を切る。
   いきなり作らせると、こちらが理解できないコードだけが増えるため。
2. **技術スタック（使う道具の組み合わせ）を社内標準として先に指定する。**
   AI に選ばせると毎回違うものを提案されるため。
3. **「私はWebの用語がわからないので、専門用語には必ず短い注釈をつけて」** と頼む。
   このREADMEの用語の補足も、この指示の結果です。

### 実際に出した指示（抜粋・原文）

開発中に出した指示は全部で250件ほどありました。流れが分かるものを時系列で抜き出します。

**① 元になる FileMaker アプリを渡して、移植の構成を出させる**

> 今新しくフォルダを作成しました。内容はFilemakerのxmlをDDRParserで分析し、テキスト化したもの
> になります。フォルダ名：バイクショップ店舗管理　この内容を分析し、WEBに作り変えてください。
> データはダミーで作成してください。（中略）**実装はまだしなくてよいので、構成を教えて**

FileMaker の DDR（設計情報の書き出し）をそのまま渡しただけで、テーブル構成と画面構成の
移植案が返ってきました。ここが一番 AI の効果が大きかった場面です。

**② 作ったあとに、元アプリとの差分を洗い出させる**

> 再度、バイクショップ店舗管理のフォルダを分析し、今のWEB画面で足りない機能があるかと思うので、
> 洗い出して。

**③ 自分で確認する基準を、先に AI に作らせる**

> WEB画面の処理やデザイン、見た目をチェックするためのチェックシートを作成してください。

> それではチェックシートをもとにチェックしていってください

チェックシートを先に作らせてから、それを基準に自己点検させる頼み方が一番効きました。
「バグがないか見て」と頼むより、具体的な指摘が返ってきます。

**④ 業務の一般論が分からないときは、作らせる前に聞く**

> 案件や見積・請求のフローがよくわかってないのですですが、一般的な考えで作り直せますか？

> 請求についてですが、作業が完了しないと発行できないんじゃない？作業が完了したかどうか何で
> 判別するの？通常のフローがわからないので教えて

**⑤ 公開前のセキュリティ対応は、やることを箇条書きで渡す**

> 公開する前に、次の4つをやってください。
> 1. 点検　鍵（APIキー・パスワード）や個人情報が、ファイルとコミット履歴に含まれていないか
>    調べて、あれば場所を報告してください
> 2. 検索対策　noindex を設定してください（robotsメタタグと robots.txt の両方）
> 3. Basic認証　（中略）認証情報は環境変数から読み、コードに直書きはしないこと
> 4. 環境変数の登録　パスワードはあなたが生成し、登録後に一度だけ平文で教えてください。
>
> ブラウザでの認可や、私の画面操作が必要なときは「ここで止まってください」と言ってください。

**⑥ 見た目の直しは、抽象的に言わず「どう直すか」を指定する**

> 他のところもそうだけど、無理して縦にしなくてもよいです。横にしてもよい。項目が多いなら
> ２段にしてもよい。横幅を考えて。

### うまくいった頼み方 / いかなかった頼み方

| | 例 | 結果 |
| --- | --- | --- |
| ○ | 「実装はまだしなくてよいので、構成を教えて」 | 作る前に方針を確認でき、手戻りが減った |
| ○ | 「チェックシートを作って」→「それをもとにチェックして」 | 自己点検の基準ができ、指摘が具体的になった |
| ○ | 「一般的にはどうなんですか」と先に聞く | 業務フローを理解してから仕様を決められた |
| ○ | 「横幅を考えて2段にして」 | 直し方まで指定すると一発で通る |
| × | 「かっこいいデザインに作り変えて」 | 好みが伝わらず、何度もやり直しになった |
| × | 「修正して」だけで終わる | 直っていないのに「修正しました」と返ってくる（後述） |

### 秘密情報の扱いについて

やりとりの途中で、データベースの接続情報（パスワードを含む文字列）をそのままチャットに
貼ってしまったことがありました。**AI に渡す文章にも、鍵や個人情報はそのまま入れない**
というのが、今回いちばん実感した注意点です。リポジトリ自体には、`.env` や `.dev.vars`
（秘密の値を書くファイル）は一度もコミットされていないことを、コミット履歴まで遡って確認済みです。

## ふりかえり

| | |
| --- | --- |
| **一番詰まったところ** | ローカルPC・GitHub・Cloudflare・Neon の4つがどう繋がっているのかが最後まで掴めず、「どこを直せば公開中の画面に反映されるのか」が分からないまま修正を重ねてしまったこと。 |
| **AI が役に立った瞬間** | FileMaker の DDR フォルダを渡しただけで、テーブル構成と画面構成の移植案が出てきたとき。自分では組み立てられなかった「案件 → 見積 → 請求」の業務フローも、一般論として説明してもらえた。 |
| **AI に騙されかけたところ** | 「修正しました」と言われても実際には直っていないことが何度もあったこと。極めつけは、別のチャットで同じAIに聞いたら「データベースは作っていない」と答えられ、実際には作られていた場面で、AIの記憶と報告は自分で確かめないと信じられないと分かった。 |

補足として、3つ目の「騙されかけた」具体例を挙げておきます。

- **割引のマイナス計算**：作業マスタに割引を追加して金額をマイナス計算にするよう頼み、
  「修正しました」と返ってきたが、実際には帳票側に反映されておらず「マイナス計算されていません」
  と2回指摘し直した。
- **本番に反映されない修正**：ダッシュボードから問い合わせフォームへのリンクを消したあと、
  ローカルでは消えているのに公開中の画面には残ったまま。「GitHubにpushすれば自動で反映される」
  という説明を信じていたが、実際には自動デプロイの設定がされていなかった。
- **DBを作った記憶の食い違い**：「データベースは私がお願いして作ってもらいましたか」と聞いたところ、
  別のチャットでは「作ったことはない」と答えられた。AIはチャットをまたぐと前の作業を覚えていない。

## 次に検討すること

1. メール通知の実装（Workersでは nodemailer が使えないため、Resend など HTTP API 型の
   サービスへの切り替えが前提）
2. 社内ダッシュボードのURLが決まったら、`trustedOrigins` とCookie共有設定を追加する
3. Docker（nginx・docker-mailserver・postgres・cloudflared）一式は停止済みだが、
   ロールバック用にリポジトリへ残してある。不要と判断できた時点で、関連ファイル
   （`docker-compose.yml` / `Dockerfile` / `nginx/` / `server.mjs`）ごと整理する
4. 以下は実務価値はあるものの規模が大きいため、必要になってから対応する方針で見送っている
   - 請求の入金消込（入金日・入金額の記録）
   - CSVエクスポート／インポート（会計ソフト連携・棚卸し用）
   - 期間で絞る詳細検索（車検期限が今月、終了予定日が今週、など）
   - 帳票のPDFをメールでそのまま顧客へ送る機能
   - 一覧のページネーション（現状は全件取得して画面側で絞り込む方針。件数が数千件規模に
     なってから対応すれば十分）
